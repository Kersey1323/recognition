# 3D重建长算力任务调度技术方案

## 一、业务背景

目前需要对约 **2万个** 配件完成3D重建，后续每年有约 **5000个** 配件更新需要重新重建。单个配件从多角度照片到最终OBJ模型的完整重建流程耗时约 **20分钟**（含COLMAP点云估计、2DGS训练、网格提取、视觉特征提取四个阶段），算力卡规格按 **RTX 5090** 级别规划。

**核心诉求**：在合理的时间窗口内消化初始存量和年度增量任务，同时保证重建服务的可用性和GPU利用率。

---

## 二、算力需求测算

### 2.1 工时估算

| 场景 | 配件数量 | 单件耗时 | 总GPU工时 | 折合天数(24h) |
|------|---------|---------|----------|-------------|
| 初始全量重建 | 20,000 | 20 min | 6,667 h | 278 天 |
| 年度增量重建 | 5,000 | 20 min | 1,667 h | 69 天 |

### 2.2 卡数规划

**初始全量阶段**——目标在 **30个自然日** 内完成：

```
所需卡数 = 6667h ÷ (30天 × 24h) ≈ 9.3 → 取 10 张卡
```

考虑到实际运行中存在任务调度间隙、COLMAP占CPU等开销，建议按 **10~12张 5090** 规划。如果工期放宽到60天，5~6张卡也能跑完。

**年度增量阶段**——假设全年均匀分布，月均约420件：

```
月度GPU工时 = 420 × 20min ≈ 140h
单卡月可用 = 30 × 24 × 0.85（利用率）≈ 612h
```

年度常态只需 **1张卡** 即可消化增量。但考虑到增量任务往往集中在几个月份，以及日常调试和模型迭代的需要，建议常态保留 **2~3张卡**。

### 2.3 推荐配置

| 阶段 | GPU数量 | 预计周期 | 备注 |
|------|---------|---------|------|
| 初始全量（赶工期） | 10~12张 5090 | 30天 | 可租用云GPU，用完即退 |
| 年度常态 | 2~3张 5090 | 全年 | 自建或长租，兼顾开发测试 |

> 初始全量如果没有时间压力，也可以用3~4张卡跑2~3个月慢慢消化，节省成本。

## 四、核心模块设计

### 4.1 消息队列（RocketMQ）

选用 **RocketMQ** 作为任务队列，原因：
- 支持消息优先级和延迟消息
- 单机吞吐量高，消息堆积能力强（百万级）
- 支持事务消息，保证任务不丢
- 原生支持消费组和广播模式，天然适配多Worker消费

Topic 设计：
```
recon-task-high      # 紧急任务
recon-task-normal    # 日常增量
recon-task-low       # 全量补录
recon-task-result    # 任务完成通知（Worker → 业务系统）
```

消息体：
```json
{
    "task_id": "uuid",
    "item_id": 12345,
    "image_source": "oss://bucket/items/12345/photos/",
    "priority": "normal",
    "trainer_type": "2dgs",
    "iterations": 7000,
    "created_at": "2026-02-24T10:00:00",
    "retry_count": 0,
    "max_retries": 2
}
```

消费模式：Worker以 **集群消费（Clustering）** 模式消费，同一条消息只被一个Worker处理，天然实现负载均衡。

### 4.2 调度器（Scheduler）

调度器的角色相对轻量，因为RocketMQ本身已经提供了消费负载均衡。调度器主要负责：

- **任务去重**：同一 `item_id` 不会同时存在两个运行中的任务，通过Redis记录正在执行的item_id
- **Worker健康检查**：通过心跳监控Worker状态
- **任务状态管理**：在Redis中维护任务状态供外部查询

### 4.3 Worker进程

每个Worker是一个独立Python进程，启动时指定GPU编号：

```bash
python -m recon_worker --gpu 0 --worker-id worker-0 --namesrv 10.0.0.1:9876
```

Worker内部流程：
```
while True:
    1. 从RocketMQ消费消息（按优先级依次订阅）
    2. 下载图片到本地临时目录
    3. 执行重建流水线:
       a. COLMAP 稀疏重建（CPU密集，约5分钟）
       b. 2DGS 训练（GPU密集，约10分钟）
       c. 网格提取+导出OBJ（GPU，约2分钟）
       d. 视觉特征提取（GPU，约3分钟）
    4. 上传结果到 MinIO/OSS
    5. 发送完成消息到 recon-task-result
    6. 清理临时文件
    7. 回到第1步
```

视觉特征提取阶段：
- 对重建使用的多角度图片提取 DINOv2 / ResNet 特征向量
- 特征向量写入 Milvus 向量数据库，用于后续的配件视觉检索
- 同时提取代表性视角的缩略图用于前端展示

### 4.4 重试与容错

**消息级重试**：
- RocketMQ 自带消费重试机制，消费失败后自动重投（默认间隔递增）
- 超过最大重试次数进入死信队列（DLQ），人工介入处理
- 常见失败原因：OOM、COLMAP匹配点过少、图片数量不足

**Worker级容错**：
- Worker进程崩溃后由 systemd / supervisor 自动拉起
- RocketMQ 消费侧有 ACK 机制，未确认的消息会被重新投递
- 多机部署时某台机器宕机不影响其他机器继续工作

## 五、任务批量导入与触发策略

### 5.1 初始全量导入

全量2万个配件分批写入RocketMQ：
```
总量 20,000 件
每批 500 件，共 40 批
每批间隔：上一批消费过半后导入下一批
```

导入脚本从数据库拉取未重建的配件列表，按 `item_id` 分页，逐批发送到 `recon-task-low`。

### 5.2 增量更新触发

**实时触发**：工装上传视频后，服务端自动发送消息到 `recon-task-normal`。

**定时批量**：每天凌晨扫描「有照片变更但未重建」的配件，批量导入。

### 5.3 优先级场景

| 优先级 | 场景 | Topic |
|-------|------|-------|
| 高 | 客户催单、临时需求 | recon-task-high |
| 普通 | 日常增量更新 | recon-task-normal |
| 低 | 全量补录、历史数据 | recon-task-low |

## 六、监控与运维

用 Prometheus + Grafana 搭监控面板。

**核心指标**：
- RocketMQ 各Topic消息堆积量
- 任务完成速率（件/小时）
- 各Worker状态和GPU利用率
- 失败率与死信队列堆积量

**告警规则**：

| 告警 | 条件 | 处理方式 |
|------|------|---------|
| Worker离线 | 心跳超时 90s | 检查进程，必要时重启 |
| 消息堆积 | 堆积>500 且持续30分钟 | 检查Worker，考虑扩容 |
| 死信队列堆积 | DLQ有新消息 | 人工排查失败原因 |
| 磁盘不足 | 剩余空间 < 50GB | 清理临时文件 |

## 七、多机部署方案

```
             ┌─────────────────┐
             │  管理节点         │
             │  RocketMQ        │
             │  Redis(状态)     │
             │  Grafana监控      │
             └────────┬────────┘
                      │ 内网
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ 计算节点A │  │ 计算节点B │  │ 计算节点C │
  │ 4×5090   │  │ 4×5090   │  │ 4×5090   │
  │ Worker×4 │  │ Worker×4 │  │ Worker×4 │
  └──────────┘  └──────────┘  └──────────┘
```

- **扩容**：新机器启动Worker加入同一消费组即可
- **缩容**：停止Worker，RocketMQ自动重新分配分区
- **图片/结果存储**：MinIO/OSS 对象存储，Worker各自下载上传

## 八、与现有Pipeline的对接

当前项目的 `ReconstructionPipeline` 已实现完整重建流程。调度系统在此基础上包装。

改造要点：
1. 新增Worker入口 `recon_worker.py`，使用RocketMQ消费端SDK
2. 重建完成后增加特征提取步骤，调用 DINOv2/ResNet 提取特征写入Milvus
3. 任务状态写入Redis供外部查询
4. 现有Web接口保持兼容，发送消息到RocketMQ

## 十一、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 图片质量差致COLMAP失败 | 该配件重建失败 | 记录原因，人工补拍 |
| GPU过热降频 | 耗时增加 | 控温，必要时降功耗墙 |
| 网络不稳致下载失败 | 任务失败 | RocketMQ自动重试 |
| 磁盘撑爆 | Worker停工 | 定时清理+告警 |
| 训练器版本更新 | 结果不一致 | 锁定版本，统一镜像 |

## 2. 修复训练进度实时上报问题

根本问题：
- `video_reconstruction` 任务使用 `subprocess.run()` 阻塞执行，无法实时读取输出
- `update_state()` 的 meta 参数使用不当，导致进度信息未正确保存到 Redis
- 缺少 `re` 模块导入

修复内容：
1. **添加缺失的 re 模块导入**：
   - 在 `tasks.py` 顶部添加 `import re`

2. **修改 video_reconstruction 任务**：
   - 从 `subprocess.run()` 改为 `subprocess.Popen()`
   - 实时读取训练输出并解析进度
   - 添加与 train_reconstruction 相同的进度追踪逻辑

3. **修复 update_progress 方法**：
   - 使用 `backend.store_result()` 直接存储进度信息
   - 将进度数据作为 `result` 参数传递（而不是 `meta`）
   - 确保数据正确保存到 Redis backend

4. **优化进度追踪逻辑**：
   - 改进正则表达式匹配，准确提取 tqdm 进度条中的百分比
   - 添加进度变化检测，避免过于频繁的状态更新
   - 优化进度映射：训练进度占 10-95%，提取结果占 98%
   - 在状态信息中包含迭代次数（如 "训练中 28520/30000"）

5. **添加测试脚本**：
   - 创建 `scripts/testing/test_celery_redis.py` 用于测试 Celery 与 Redis 连接
   - 创建 `scripts/testing/test_celery_progress.py` 用于模拟和验证进度更新
   - 验证状态更新和读取是否正常工作

影响文件：
- csrcqsf/biz/railwayparts/reconstruction_server/tasks.py - 修复两个任务的进度追踪
- scripts/testing/test_celery_redis.py - 新增测试脚本
- scripts/testing/test_celery_progress.py - 新增测试脚本

## 5. 新增功能：自动同步重建任务状态

问题：列表接口返回的任务进度不会自动更新，只有调用"查询任务状态"接口时才会同步

解决方案：添加后台定时任务，自动同步所有进行中任务的状态

实现内容：
- 在 `csrcqsf/scheduler.py` 中添加 `sync_reconstruction_tasks_sync()` 同步函数
- 使用 APScheduler 的 interval 触发器，间隔时间可通过环境变量配置
- 自动查询所有 pending 和 training 状态的任务
- 从 Celery 获取最新状态并直接更新数据库（使用同步 SQLAlchemy）
- 添加错误处理和日志记录
- 在 `csrcqsf/app.py` 中导入 scheduler，确保应用启动时自动开始定时任务
- 使用同步数据库操作避免事件循环冲突（解决 "attached to a different loop" 错误）
- 添加环境变量 `RECONSTRUCTION_SYNC_INTERVAL` 配置同步间隔（默认10秒）

优势：
- 列表接口直接返回最新数据，无需前端轮询
- 减少 Redis 查询压力（集中查询而非分散查询）
- 同步间隔可配置（通过环境变量 `RECONSTRUCTION_SYNC_INTERVAL`，建议5-30秒）
- 使用同步数据库操作，完全避免事件循环冲突
- 集中管理，便于监控和调试

新增测试脚本：
- scripts/testing/test_scheduler.py - 测试定时任务调度器
- scripts/testing/test_app_startup.py - 测试应用启动时定时任务是否自动开始
- scripts/testing/test_sync_task.py - 测试重建任务状态同步功能（异步版本）
